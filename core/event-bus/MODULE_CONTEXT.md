## Purpose

The event-bus module defines the subscription and delivery contract for HomeSynapse's in-process event distribution system. It is a pull-based, notification-driven bus: the EventBus does not deliver events directly to subscribers — it notifies matching subscribers that new events are available, and subscribers pull events from the EventStore themselves. This design enables backpressure, coalescing, and crash-safe checkpoint-based resumption. The module also defines the CheckpointStore interface for durable subscriber position tracking, ensuring that subscribers resume from the correct position after crashes. **Since BUS-ORDER-1 (2026-09-12, AMD-101 §2) the realization matches that sentence exactly: the notification is a wake hint, delivery is the bus's read-forward from the subscriber's in-memory cursor, and the persisted checkpoint is the durable floor for restart — never a delivery guard (the section below).**

As of M3.2, the module implements the full three-phase REPLAY→TRANSITION→LIVE algorithm (AMD-42 §3.4.2). M3.1 landed the bus skeleton: per-subscriber virtual thread lifecycle, mode FSM (COLD → REPLAY → TRANSITION → LIVE → SUSPENDED), supervisor with exception taxonomy and circuit breaker, in-memory DLQ ring, and per-subscriber isolation guarantees (INV-SUB-ISO-01..06). M3.2 added: `ReplayDriver` (page-replay loop from persisted checkpoint with AMD-38 checkpoint cadence and overflow restart), `TransitionCoordinator` (drains the `ReplayWindowQueue` with gap detection, atomically promotes to LIVE, fires `onCaughtUp()` exactly once), the bounded thread-safe `ReplayWindowQueue` (10,000-entry cap, latched overflow flag), and the LIVE pull loop with per-event checkpointing.

M3.3 adds backpressure metrics and observability (AMD-43): the `BusMetrics` typed facade with JFR-native production implementation, the seven canonical bus metric names (Decision 1 of M3.3 deliberation), hysteresis-based `QueueSaturationHealthCheck`, and per-subscriber `DerivedWriteRateLimit` token-bucket. The bus's notification path now samples writer queue depth via an injected `IntSupplier` (DEC-M3-14), emits the depth gauge on every notification, increments a publisher-blocked counter when depth exceeds 5000 (INV-BUS-02 — record only, never block), and records subscriber lag after each successful LIVE delivery. No new ArchUnit rules; no new `requires` directives (jdk.jfr is a platform module).

## BUS-ORDER-1 (2026-09-12) — the read-forward model (AMD-101 §2; instruction `nexsys-hivemind/context/instructions/2026-09-12_coder-lane_BUS-ORDER-1_read-forward-live-delivery_coding-instruction.md`)

**The invariant (Nick's acceptance bar, `context/planning/2026-09-12_v71_BUSFIX-b_ruling-of-record.md` §2):** every position whose event matches a LIVE subscriber's filter is delivered to that subscriber exactly once, in position order, regardless of the order in which notifications arrive. Pinned by `ReadForwardDeliveryTest` (T1 the LIVE path with reversed notifies · T2 the flip with reversed notifies in the replay window · T2b an append between the drain's page read and the CAS · T3 an append with no notification, delivered within 2 × `liveIdleTick`) and by `DeliveryAnomalyEmissionTest`, re-pinned to the page semantics.

- **The cursor.** `SubscriberRuntime.cursor()` (an `AtomicLong`; `advanceCursor(long)` is a CAS-max returning `true` when it advanced; LTD-11) is the highest position delivered OR filtered past in this activation. `ReplayDriver.run()` initialises it from the persisted checkpoint and advances it past every paged position; `TransitionCoordinator.drainAndPromote` and `InProcessEventBus.liveLoop` advance it per envelope through the shared step. It never moves backwards. `InProcessEventBus.lastDelivered(String)` (public, concrete-only — the `abandon()` precedent; `-1` for an unknown id) exposes it; `SubscriberSnapshot` is unchanged (7 fields).
- **The per-envelope step.** `InProcessEventBus.deliverStep(runtime, envelope, checkpointStore)` (package-private static; the LIVE loop and the drain both call it): non-matching → `advanceCursor`, `FILTERED`; matching → `supervisor.deliver`: `SUCCESS` → `advanceCursor` then, if it advanced AND `!atomicCheckpoint()`, `writeCheckpoint(id, position)` → `DELIVERED`; `PARKED` → `advanceCursor` (the DLQ row holds it — today's semantic) → `PARKED`; `CIRCUIT_BREAKER_TRIPPED` / `INFRASTRUCTURE_FAILURE` → `STOP` (the supervisor already SUSPENDED). **The persisted checkpoint follows the cursor and is therefore monotonic by construction (INV-PROJ-04); it is written only after a matching SUCCESS, so for a type-filtered subscriber it rests BELOW the cursor by the trailing non-matching span — by design; REPLAY re-reads and re-filters that span on restart.** The atomic projection (`state_projection`, AMD-45 §2.2): the cursor advances, the bus-side write stays skipped, its own sink is untouched.
- **The LIVE loop.** On a wake or the idle tick: `drainHints()` (the queue's values are ignored) → `readFrom(cursor, liveReadBatch)` through the subscriber's `SubscriberReadExecutor` → `deliverStep` per envelope in position order, `recordSubscriberLag(id, remainingInPage + hints, lagMillis)` after each `DELIVERED` → repeat while the page was full → on an empty or short page, `LockSupport.parkNanos(liveIdleTick)` **only if the hint queue is still empty** (a hint that arrived since the drain means "read again now"). A page read that throws → ONE `LIVE_READ_FAILED` at `cursor + 1`, then the next tick retries (no bounded attempts, no SUSPEND). Exits on interrupt or SUSPENDED. A re-entrant publish from inside `onEvent` wakes the same loop — one extra page read at most, no special case.
- **GOTCHA — the unpark permit is NOT a reliable wake carrier; the hint queue is (measured 2026-09-12, JDK 21.0.4).** `LockSupport.unpark(vt)` sets one permit; a permit that lands while the virtual thread is parked ANYWHERE ELSE — the read executor's `Future.get()` (production's `SqliteSubscriberReadExecutor` shape), a re-entrant publish's write-future wait, a lock — is spent by that park's resume (the desk probe: `parkNanos(2 s)` after a completed `Future.get()` blocked its full 2 s whenever an unpark had landed during the wait; only an unpark on a RUNNING thread survives to the next park). With the tick as the only fallback that was 49 of 200 hero loops at `~275 ms` (one tick + the 25 ms chain) and 4 at `~555 ms` (two ticks), deterministic under two carriers and unpinned alike; with the queue check before the park: see the BUS-ORDER-1 return §0 (`ReadForwardDeliveryTest` T5 pins it with a future-backed read executor and a 50 ms gap between the wake and the read's completion — the gap is what makes the JDK behaviour deterministic).
- **The notification.** `notifyEvent(P)` / `offerUnfiltered(P)`: for an ACTIVE subscriber there is NO persisted-checkpoint guard any more — `routeByMode` (mode read under the queue lock, as before): REPLAY/TRANSITION → `replayWindowQueue.enqueue(P)` (a hint; overflow → the REPLAY restart, unchanged), LIVE → `runtime.wake(P)` (offer the position as a hint + `LockSupport.unpark(vt)`), COLD/SUSPENDED → nothing. `notifyEvent` still filters before waking (a non-matching event wakes nobody; the read-forward filters again on its own read). Passive registrations keep their guard (callbacks, not loops). `NOTIFY_SKIPPED_LIVE` is unreachable. **The publisher's thread no longer reads the checkpoint store per active subscriber per publish.**
- **The flip.** `drainAndPromote`: drain the hints → `readForwardToHead()` (pages of `readBatch` from the cursor, `deliverStep` each; a page read that throws → SUSPEND + `return false`, the REPLAY arm's shape, no anomaly) → under `queue.lock()`: empty → CAS TRANSITION→LIVE + `setMode(LIVE)`; a hint that landed in between → read forward once more. `onCaughtUp` single-shot unchanged. The gap detection on `lastReplayedPosition` is GONE (hints carry no positions to gap-detect); `lastReplayedPosition` is REPLAY's own high-water mark now (set by `ReplayDriver` only). Constructor `(runtime, eventStore, checkpointStore, clock, int readBatch)` — the FIX-1a emitter parameter is gone (nothing emits from the drain).
- **`EventBusConfig` 2 → 4 fields:** `int liveReadBatch` (≥ 1; default 64 = `DEFAULT_LIVE_READ_BATCH`) and `Duration liveIdleTick` (≥ 1 ms; default 250 ms = `DEFAULT_LIVE_IDLE_TICK`); `HOME_DEFAULT = (10_000, 5_000, 64, 250 ms)`; a 2-arg convenience constructor supplies the defaults so the M3.6b construction sites (`EventBusConfigTest` ×3, `HOME_DEFAULT`) are byte-unchanged. Pinned by `EventBusConfigLiveFieldsTest`. `HomeSynapseConfig` (lifecycle) passes `HOME_DEFAULT` — no YAML loader constructs the record.
- **Retained kinds (INV-GA-02), never emitted since BUS-ORDER-1:** `LIVE_READ_EMPTY`, `LIVE_READ_EXHAUSTED`, `TRANSITION_READ_EMPTY`, `TRANSITION_READ_EXHAUSTED`, `NOTIFY_SKIPPED_LIVE`. Still emitted: `NOTIFY_NOT_VISIBLE` (the publisher's own empty page, then the unfiltered wake) and `LIVE_READ_FAILED` (once per failed LIVE page read). `LIVE_READ_ATTEMPTS` / `LIVE_READ_BACKOFF_FIRST_NANOS` / `DRAIN_READ_ATTEMPTS` / `DRAIN_READ_BACKOFF_FIRST_NANOS` and `readLivePosition` / `readQueuedPosition` are removed.
- **The census rule (lifecycle's `BusPositionCensusIT`):** `DELIVERED(S,P) := P <= lastDelivered(S)` — the in-memory cursor through the concrete bus, so the census is exact by construction; its line gains ` delivered_max=<D>` beside ` checkpoint=<C>`; ` pending=<Q>` now counts un-consumed wake hints. The await diagnostic (`BusAwaitDiagnostic`) prints ` cursor=<K>` after ` checkpoint=` and renames ` pending=` to ` hints=`; a timeout adds `bus.head: position=<H> type=<T>` + up to three `bus.tail:` lines (lifecycle MODULE_CONTEXT).
- **Gotcha — `pendingDepth` changed meaning.** It is the count of un-consumed wake hints (offered positions the loop has not drained yet), no longer "undelivered positions": `hints ≥ 1` with the cursor below the head = woken and not yet read; `hints = 0` with the cursor below the head = no wake since the last drain (the idle tick's case). `SubscriberSnapshot`'s shape is unchanged.
- **Gotcha — a subscriber now receives every matching position in the store beyond its cursor, notified or not.** A test that appends without `notifyEvent` and expects NO delivery to an active LIVE subscriber is wrong under the read-forward (it is delivered within one idle tick); passive registrations (the callback bridge) are still notification-only.

## JPMS Module

```
module com.homesynapse.event.bus {
    requires transitive com.homesynapse.event;
    requires jdk.jfr;

    exports com.homesynapse.event.bus;
}
```

The `requires transitive` on event-model means any module that reads `com.homesynapse.event.bus` automatically gets access to all event types, `EventEnvelope`, `EventPublisher`, `EventStore`, and (transitively) all platform-api identity types.

The non-transitive `requires jdk.jfr` (added M3.3) lets the bus emit JFR custom events from `BusMetricsJfr`. Despite shipping with the JDK, `jdk.jfr` is NOT in `java.base` and is NOT auto-required — JPMS demands the explicit directive. Consumers of `com.homesynapse.event.bus` do NOT see `jdk.jfr` transitively: the JFR event classes are package-private implementation details and never appear in exported API signatures.

## Cross-Module Contracts

- **Pull-based subscription model.** The EventBus does NOT deliver events to subscribers. It wakes them via `LockSupport.unpark()`. Each subscriber is responsible for calling `EventStore.readFrom()` to pull events starting from their checkpoint position. Since BUS-ORDER-1 (2026-09-12) the bus's own LIVE loop performs that read-forward for active subscribers — from the in-memory cursor, in pages of `liveReadBatch`, woken by the hint or the idle tick — and hands each matching envelope to `Subscriber.onEvent`.
- **At-least-once delivery with subscriber idempotency.** If the system crashes between event persistence and checkpoint update, the subscriber will re-process events from its last checkpoint on recovery. Subscribers MUST be idempotent (INV-ES-05).
- **Backpressure coalescing for DIAGNOSTIC events.** Non-exempt subscribers may have DIAGNOSTIC-priority events coalesced during high throughput.
- **Subscriber positions start at 0.** If `CheckpointStore.readCheckpoint()` returns 0 for a subscriber, it means the subscriber has never checkpointed and should start from the beginning of the event log.
- **`SubscriptionFilter.matches()` is a conjunction.** An event must satisfy ALL active filter criteria to pass.
- **`subscribeRuntime` creates full per-subscriber runtime.** VT, dedicated read connection, supervisor, DLQ, mode FSM. The subscriber starts in COLD and transitions to REPLAY asynchronously.
- **`subscribe` is passive.** Filter evaluation + checkpoint tracking only. No VT, no supervisor, no DLQ. Backward compatible with Phase 2 contract tests.
- **Bus does NOT have a `publish()` method.** Publishing is EventPublisher's job. The bus is notification-only.

## Key Design Decisions

1. **Pull-based, not push-based delivery.** Subscribers are woken (notified) but pull events themselves from EventStore.
2. **`CheckpointStore` is a separate interface from `EventStore`.** Different consumers, same database.
3. **`subscriberId` is a plain String, not a typed wrapper.** Infrastructure components don't need ULID identity.
4. **`SubscriptionFilter` uses `Set<String>` for event types.** Extensible strings, not a closed enum.
5. **New EventBus methods are `default` with UnsupportedOperationException.** Allows InMemoryEventBus (Phase 2 fixture) to compile without modification.
6. **SubscriberInfo stays 3-field (DP-3/DP-6).** All introspection goes through SubscriberSnapshot, not SubscriberInfo.
7. **Bus module is JDBC-free (DP-4).** SubscriberReadConnectionFactory/Executor keep java.sql out of module-info.
8. **Infrastructure exception carve-out (DP-1).** Error, IOException, and non-RuntimeException checked exceptions → immediate SUSPENDED. Only RuntimeException follows backoff path.

## Gotchas

- **Notify order ≠ append order (FIX-2b-ii, 2026-09-12; REV-1 F3/F4).** `NotifyingEventPublisher` (lifecycle) calls `notifyEvent(P)` on the PUBLISHER's thread after its own append, with no lock across the pair, so two publishers' notifies can reach a subscriber out of position order. Two consequences for a LIVE subscriber: (a) delivered `[P+1, P]` writes the checkpoint `P+1` then `P` — `SqliteCheckpointStore`'s upsert is `INSERT OR REPLACE` with no monotonic guard, so the persisted checkpoint REGRESSES to `P` while both were delivered (TR-1's census, `DELIVERED := checkpoint ≥ P`, then reports `missed=1 first_missed=P+1` — the exact tuple of ci samples #11/#12); (b) if `P+1` was delivered before `P`'s notify arrived, the guard `checkpoint >= P` skips `P` for good — a silent drop that the census cannot see (it counts `P` as delivered) and that kind `NOTIFY_SKIPPED_LIVE` now names. **FIXED by BUS-ORDER-1 (2026-09-12, the section near the top):** the LIVE path has no checkpoint guard (a wake is never skipped), delivery is the read-forward from the cursor (position order, exactly once), and the checkpoint follows the cursor (monotonic). `ReadForwardDeliveryTest` T1 forces the drop arm deterministically; T2 exposed the drain's twin — at `5f918c7` the drain's gap detection (`position <= lastReplayedPosition → continue`) DROPPED every queued position below a higher one delivered before it (reversed hints `[P+2, P+1, P]` in the replay window delivered `P+2` only).

**GOTCHA: `InMemoryEventBus` is NOT modified in M3.1.** It remains the Phase 2 fixture for the original 4-method interface. The production bus is InProcessEventBus.

**GOTCHA: `InMemoryEventBusTest` and `InProcessEventBusTest` both extend `EventBusContractTest`.** The new Tiers 5-10 use `assumeTrue(supportsActiveRuntime())` to skip for InMemoryEventBusTest.

**GOTCHA: The supervisor's `computeBackoff()` / `sleepForBackoff()` / `MAX_RETRIES = 5` are dead code as of M3.1 and remain so after M3.5b-supervisor-wiring (2026-05-19).** The current `deliver()` parks on first failure (`attemptCount = 1`) and returns `PARKED` — there is no in-call retry loop. The future retry-loop WU will: (1) move `recordCrash()` to the post-exhaustion site so transient retries do not pollute the breaker window; (2) lift `attemptCount` to `MAX_RETRIES + 1` at park time; (3) park only after `MAX_RETRIES` exhaustion. Until then, every `RuntimeException` produces one DeadLetter row AND one crash-window increment. Do NOT reference `computeBackoff()`/`sleepForBackoff()`/`MAX_RETRIES`/`MIN_BACKOFF_MS`/`MAX_BACKOFF_MS`/`JITTER_FACTOR` from new code — they are reserved for the retry-loop wiring.

**GOTCHA: `DeadLetter.causeMessage` MUST be null-guarded by the supervisor.** `RuntimeException.getMessage()` can return `null` (e.g., `new NullPointerException()` with no constructor message). The V002 `cause_message TEXT NOT NULL` column and `DeadLetter`'s compact constructor both reject `null`. `SubscriberSupervisor.deliver()` coerces null to empty string via `e.getMessage() != null ? e.getMessage() : ""`. Any future site that constructs a `DeadLetter` from a caught Throwable must apply the same guard.

**GOTCHA: `ReplayWindowQueue` exposes `lock()/unlock()` for compound atomic operations.** Both `InProcessEventBus.notifyEvent` (mode-read + routing) and `TransitionCoordinator.drainAndPromote` (empty-check + TRANSITION→LIVE CAS) hold the queue's lock across the compound action — without this, an enqueue could interleave between the coordinator's empty-check and CAS, stranding events. The lock is a `ReentrantLock` (LTD-11). Callers must follow strict `lock()` / `try { ... } finally { unlock(); }` pairing.

**GOTCHA: `ReplayWindowQueue.enqueue(long)` returns `boolean`.** It returns `false` on overflow (queue is at 10,000) and latches an `overflowed()` flag. The bus's `notifyEvent` does NOT throw on overflow — the latched flag is the signal. The `ReplayDriver` polls `overflowed()` between page iterations; on detection it re-reads the persisted checkpoint via `CheckpointStore.readCheckpoint`, resets its internal cursor, clears the queue, and restarts the page-replay loop. Overflow is recoverable (at-least-once delivery), not data loss.

**GOTCHA: `lastReplayedPosition` is REPLAY's own high-water mark — not the checkpoint and (since BUS-ORDER-1, 2026-09-12) not the flip's hand-off.** It tracks the highest `globalPosition` for which delivery was *attempted* (success or PARKED) through the supervisor during REPLAY (set by `ReplayDriver` only; reset to the checkpoint on an overflow restart). The flip hands the CURSOR (`SubscriberRuntime.cursor()` — delivered OR filtered past, CAS-max, never reset), which `TransitionCoordinator` reads forward from; the gap detection that read `lastReplayedPosition` is gone. INV-BUS-01's text still names `lastReplayedPosition` as the drain's dedup mechanism — the cursor supersedes it (a docs-register clause for the hub, filed in the BUS-ORDER-1 return).

**GOTCHA: `onCaughtUp()` exceptions become a synthetic DLQ entry, not a normal supervisor crash.** Per AMD-42 §3.4.3, an exception from `Subscriber.onCaughtUp()` does NOT go through `SubscriberSupervisor.deliver` — it bypasses the crash-window counter, backoff, and circuit breaker. Instead, `TransitionCoordinator` catches the throwable directly and parks a `SubscriberDlq.DlqEntry` at the synthetic position `CAUGHT_UP_TRANSITION_MARKER = -1L`. The subscriber remains in LIVE mode regardless.

**GOTCHA: M3.2's LIVE loop writes a per-event checkpoint after each successful delivery.** This differs from REPLAY's AMD-38 batched cadence (200 events OR 2 s). Rationale: LIVE delivery is event-by-event with single-position reads, so per-event checkpointing has negligible overhead and minimises lag against the log head. AMD-38's WAL-pressure concern applies to the continuous-reader pattern in REPLAY, not to LIVE.

**GOTCHA (M4.0a, AMD-45 §2.2 / AMD-45-INV-01): ALL THREE bus subscriber-checkpoint writers are gated on `!runtime.info().atomicCheckpoint()`.** AMD-45-INV-01 ("neither the subscriber checkpoint nor the view checkpoint advances without the other") is unconditional — it does NOT carve out REPLAY. For an `atomicCheckpoint = true` subscriber the projection's coupled `AtomicCheckpointSink` (state-store) is the **sole** subscriber-checkpoint writer in BOTH phases; the bus writes nothing. The complete bus-side writer set (verified by `grep '\.writeCheckpoint('` over `core/event-bus/src/main/java`; three sites again since BUS-ORDER-1, 2026-09-12):
- `InProcessEventBus.deliverStep` (BUS-ORDER-1 — the ONE per-SUCCESS-delivery write, shared by the LIVE loop and the TRANSITION drain; written only when the cursor advanced, so monotonic) — gated. It replaces the two per-delivery sites that FIX-1b's `TransitionCoordinator` write and M3.2's `liveLoop` write used to be.
- `ReplayDriver` final tail write — gated (M4.0a correction).
- `ReplayDriver` periodic AMD-38-cadence write — gated (M4.0a correction). Cadence counters still reset when gated, so loop timing is unchanged; only the uncoupled write is suppressed.

**Why the REPLAY gate is load-bearing, not optional (M4.0a D-1 adjudication):** `StateProjection.onEvent` applies state and calls `advanceCheckpointCadence` in REPLAY/TRANSITION (only COLD/SUSPENDED short-circuit), so the projection writes its coupled checkpoint *during* REPLAY. Leaving the `ReplayDriver` writes ungated created two independent writers to the `subscriber_checkpoints` row on different cadences — a crash mid-REPLAY over a >200-event log left subscriber@N > view@M, and on restart the bus resumed at N+1 while the view was at M, losing events M+1..N. That is the exact window AMD-45-INV-01 closes, reopened on the REPLAY path — precisely the production reconciliation / first-boot-large-log scenario REC-80's metric exists to measure. The `ReplayDriver`'s initial-checkpoint read (run()) and overflow-recovery read naturally resume from the projection's coupled checkpoint, so suppressing the bus writes is safe (re-replay is idempotent, AMD-45 §2.3). Regression: `EventBusContractTest` Tier 9 `replayDoesNotAdvanceBusCheckpointForAtomicCheckpointSubscriber` (201-event REPLAY; asserts the atomic subscriber's bus checkpoint stays 0 while a non-atomic control advances to the tail) — FAILS without the `ReplayDriver` gates.

The adapter wraps the JFR events; it does not replace the emission path. This is **accepted design debt, not a gap**.

**GOTCHA: `BusMetrics.recordPublishLatency` is recorded by `InProcessEventBus.notifyEvent` itself, not by the upstream `EventPublisher`.** The bus measures the wall-clock duration of its notification fan-out as the bus-side contribution to overall publish latency. End-to-end publish latency from `EventPublisher.publish()` (persist + notify) is a future production-wiring concern. The metric name is canonical (AMD-43 §3.6.2); the measurement point is a deliberate scope-trimmed choice for M3.3.

**GOTCHA: `BusSubscriberLagEvent` carries both lag-events and lag-millis in a single JFR event.** The seven logical metric names map to six JFR event classes because subscriber lag has both observations emitted from a single observation point in `liveLoop` after successful supervisor delivery. The JFR consumer (`MetricsStreamBridge`) can produce two separate `MetricSnapshot`s from one event payload.

**GOTCHA: `lagEvents` approximates the queue-tail distance via `runtime.pendingPositions().size()`.** This avoids an extra event-store query on every successful delivery (which would burn carrier-thread budget on the read executor). The approximation is correct in the steady state but lags an extra catch-up burst by one delivery interval. Production wiring may revisit this if a direct writer-tail observation becomes available cheaply.

**GOTCHA: `QueueSaturationHealthCheck` does NOT own a scheduler.** M3.5a did NOT wire this (scope was state-store only). Production wiring (lifecycle module, post-M3.5a) calls `tick()` from a 1-second `ScheduledExecutorService` task. Tests call `tick()` directly with a fixed clock to keep timing deterministic — the constructor takes only the algorithm parameters, not a scheduler. The brief's reference to a "shared supervisor scheduler" is forward-looking; the supervisor does not currently own one.

**GOTCHA: `subscriberTransitionsColdToReplayOnFirstScheduling` was relaxed in M3.2.** With M3.2's full algorithm, an empty store completes COLD→REPLAY→TRANSITION→LIVE in microseconds — the test now asserts `isIn(REPLAY, TRANSITION, LIVE)` rather than `isEqualTo(REPLAY)`. The same broadening applies to `subscribeRuntimeStartsInColdMode`. The original strict mode equality was an M3.1 artifact of the placeholder loop that never advanced past REPLAY.

**GOTCHA: `InProcessEventBus.abandon()` is on the CONCRETE class, NOT on the `EventBus` interface (M3.7).** Adding it to the interface would force every `EventBus` implementation (including the Phase 2 `InMemoryEventBus` testFixture and the new `MinimalEventBusStub`) to grow an `abandon()` override they cannot meaningfully implement — neither has live subscriber VTs or read-connection executors. The composition root (`HomeSynapseCore`) holds the concrete `InProcessEventBus` field type, so `eventBus.abandon()` resolves through normal Java dispatch without an interface method. Callers that want to reach `abandon()` from a context typed as `EventBus` must cast — and there is no good reason to do so in production. Mutual exclusion with `unsubscribe(String)` is enforced via a `volatile boolean abandoned` flag set under the existing `rwLock` write lock (LTD-11 — same lock that guards subscribe/unsubscribe). The flag check happens BEFORE acquiring the write lock to keep the no-op path cheap.

**The bus invokes `subscriber.setMode(newMode)` immediately after each successful `runtime.mode` CAS (M3.7 fix round 4).** Wired at all REPLAY/TRANSITION/LIVE/SUSPENDED transitions in `ReplayDriver`, `TransitionCoordinator`, and `SubscriberSupervisor`. Subscribers that track their own mode (e.g., `StateProjection.currentMode`) override `Subscriber.setMode` to stay in sync with the bus's authoritative FSM; subscribers that do not care about mode inherit the no-op default. **One intentional gap:** `InProcessEventBus.resume(String)` (line 342) calls `runtime.transitionTo(REPLAY)` but does NOT call `subscriber.setMode(REPLAY)` — this is the same site as the separately-tracked VT-respawn gap (PROJECT_SNAPSHOT.md Tracked Gap #2). When that gap is closed, this setMode call lands with it. Until then, do not call `bus.resume()` from production code paths that depend on the subscriber observing the mode change.

**HISTORY — superseded by BUS-ORDER-1 (2026-09-12): the LIVE loop and the drain now page forward from the cursor; the paragraph below describes the realization from `5ed9178` to `5f918c7`. GOTCHA (FAILCHAN-FIX-1a, 2026-09-05): the LIVE loop never paged forward from the checkpoint — a position not offered was a position not delivered, and a position offered but not READ was lost to that subscriber.** `liveLoop` processes only positions `notifyEvent` offered into `pendingPositions` and issues ONE single-position read per offer (`readFrom(pos - 1, 1)` through the subscriber's read executor); `drainAndPromote` does the same for queued positions. If that read returns an empty page or throws, the loop `continue`s and the next successful delivery writes a checkpoint PAST the lost position — nothing re-reads it. `notifyEvent`'s own read of the same position is a fourth arm: an empty page there offers the position to NO subscriber. Before FIX-1a all four arms were unlogged (the grounding audit `context/audits/2026-09-04_v63-b1_boot-grounding_executive-model-and-intake.md` §4 S4). Since FIX-1a every arm emits one `DeliveryAnomaly` BEFORE its `return`/`continue`. **Since FIX-1b (DP-2, same day) a drop is never a skip:** the LIVE loop and the TRANSITION drain retry the read 5× with a doubling park and then SUSPEND the subscriber honestly (`LIVE_READ_EXHAUSTED` / `TRANSITION_READ_EXHAUSTED`); `notifyEvent`'s empty page still emits and then offers the position UNFILTERED to every active subscriber (the loops filter after their own read). The checkpoint is never written for a position that was not delivered. Pins: `DeliveryAnomalyEmissionTest` T5–T7, T-R1, T-R2.

**GOTCHA (FIX-1b, 2026-09-05): a publish burst that ends inside TRANSITION used to leave the checkpoint at the REPLAY tail — every event delivered, none of the TRANSITION ones checkpointed.** `drainAndPromote` delivered queued positions but never wrote a checkpoint; the next LIVE delivery would have caught the checkpoint up, but if no further event arrived the persisted position rested at the REPLAY tail (`ReplayTransitionIT` phase 1: `Checkpoint … did not reach 1000 within 15000 ms` — reproduced on the desk 2 of 36 runs pinned to 2 carriers WITHOUT load; the loaded subscriber is still in REPLAY when the burst ends and REPLAY checkpoints its tail, so the loaded shape never showed it). Since FIX-1b the drain checkpoints each SUCCESS delivery (gated on `!atomicCheckpoint()`, the AMD-45 §2.2 rule). Pin: `DeliveryAnomalyEmissionTest.transitionDeliveries_advanceCheckpoint` — the concurrent burst is run INSIDE the driver's tail page read (one thread, the real interleaving; the FAILCHAN §10-O pattern). The instrument for the next red is FIX-1a's `(resting checkpoint N)` stamp in `ReplayTransitionIT.awaitCheckpoint` (bounds unchanged).

**GOTCHA (FIX-1a): the anomaly emitter's contract.** Invoked on the OBSERVING thread — the publisher's thread for `NOTIFY_NOT_VISIBLE`, the subscriber's virtual thread for the other kinds — so it must be safe to call from any thread and must not block. The bus wraps every call in `try/catch (RuntimeException)` and swallows: an instrument must never become a failure channel (`DeliveryAnomalyEmissionTest` T4 pins it — a throwing emitter neither escapes `notifyEvent` nor kills the subscriber's VT). The composition root (lifecycle) owns the transport: one SLF4J WARN, grep-stable token `bus.delivery_anomaly: kind= subscriber= position= detail= at=`. **GOTCHA (FIX-1a): the `-PvtParallelism=N` Gradle property is a DESK-ONLY knob; carrier COUNT, not CPU speed, is what shapes a runner.** `homesynapse.java-conventions.gradle.kts` adds `-Djdk.virtualThreadScheduler.parallelism=N -Djdk.virtualThreadScheduler.maxPoolSize=N` to the test JVM when the property is set; CI never sets it.
