# configuration — `com.homesynapse.config` — 38 types — YAML 1.2 config loading, JSON Schema validation, AES-256-GCM secrets + per-scope key management (ScopeKeyManager, M6.2; **at-rest payload counter-nonce path `encryptPayload` + `EncryptionScope` registry + durable per-scope nonce store, M6.3**), hot reload

> **AB-4 (2026-06-28): F3 nonce-construction fence + F13b fail-closed nonce-counter fsync + AAD overloads.** **F3 (programmatic, was doc-only):** `StandardScopeKeyManager` now binds each scope to exactly one GCM **nonce construction** on first encrypt — `RANDOM_IV` via `encrypt` (the `config_secrets` secrets path) or `COUNTER` via `encryptPayload` (the `[identity, presence_personal]` event path) — and rejects a cross-construction call with an `IllegalStateException` (a `(key, nonce)` collision across constructions breaks GCM confidentiality + authenticity, NIST SP 800-38D §8.3). First-use-wins, in-memory (`scopeConstruction` map); `decrypt` is construction-**neutral** (does not bind), so a fresh manager can decrypt a stored payload before it ever encrypts in that scope (the read-on-restart path). The MVP scope sets are disjoint, so a real boot never mixes — the guard catches a future wiring mistake. **F1 AAD overloads:** `ScopeKeyManager` gains `encryptPayload(scopeId, plaintext, byte[] aad)` and `decrypt(scopeId, keyVersion, ciphertext, iv, byte[] aad)`; the existing 2-arg/4-arg forms remain, delegating with an empty `NO_AAD` (secrets bind no AAD). `runGcm` calls `updateAAD` only when non-empty — so secrets + DEK wrap/unwrap (both `NO_AAD`) are byte-identical to before. **F13b (fail-closed nonce-counter fsync):** `AtomicYamlWriter.writeAtomicallyDurable` is a new durable variant used ONLY by `persistNonceCountersLocked` — a directory-entry fsync that genuinely fails on a POSIX filesystem (the channel opens but `force()` throws) raises an `UncheckedIOException` (a non-durable OR-M6-NONCE high-water mark could replay a nonce on crash → catastrophic GCM reuse, so the encrypt fails closed); a platform that cannot open a directory channel at all (Windows/non-POSIX) is tolerated (durability rides the journal). `scope_keys.json` + `secrets.enc` keep the best-effort `writeAtomically` (the Windows-safe scoping). The **rotate-DEK-on-restore boot contract (R-α REC-235)** is carried (refuse-to-encrypt until a fresh DEK version is installed or the counter is proven ≥ all priors); the restore mechanics are the backup/restore WU. **Zero-edge** (no `module-info`/`build.gradle.kts` change). Tests: `ScopeKeyManagerPayloadNonceTest` (F3 reject + AAD downgrade-resistance; the old `fence_randomIvPathUnchanged` was rewritten to disjoint scopes), `AtomicYamlWriterDurableTest` (F13b fail-closed + Windows-not-broken). Deferred build gate: `./gradlew check` not run in-session.

> **AB-3 (2026-06-19): public assembly entry-point added.** `ConfigurationServiceFactory.create(Path configDir, Clock, SystemId, EventPublisher) → Assembly(ConfigurationService service, SchemaRegistry schemaRegistry)` is the first public way to construct a `ConfigurationService` (the `StandardConfigurationService` 12-arg ctor, `StandardSchemaRegistry`, and `JsonSchemaCompositeValidator` are all package-private, so the factory lives in this package). It sources the `(major, minor)` pair from single `CONFIG_SCHEMA_MAJOR=1`/`CONFIG_SCHEMA_MINOR=0` constants and wires the identical pair into BOTH the registry and the service — so the "wired twice must match" mismatch is impossible by construction. It builds the resolving `SecretStore` (`SecretStore.create(configDir, ScopeKeyManager.create(configDir, clock), clock)`), passes `System::getenv` as the `!env` lookup, and empty migrators/listeners. The composition root registers core schemas on the returned `schemaRegistry` BEFORE calling `service.load()`.

## Purpose

The Configuration System is the single authority for reading, validating, reloading, and persisting the canonical HomeSynapse configuration. It translates human intent expressed in YAML files into validated, typed runtime state that governs every other subsystem. Every subsystem — Event Bus, Device Model, State Store, Persistence Layer, Integration Runtime, Automation Engine — receives its configuration from this module's `ConfigModel` rather than parsing YAML independently. The module also manages the encrypted secrets store, JSON Schema composition from core and integration fragments, hot reload with per-key change classification, the UI/API write path with optimistic concurrency, and forward-only schema migration. This Phase 2 specification defines the public API contracts (interfaces, records, enums, exceptions) that external modules compile against. Implementation code (SnakeYAML Engine parsing, JSON Schema validation, AES-256-GCM encryption, reload diff computation, atomic file writes) is Phase 3.

## Design Doc Reference

**Doc 06 — Configuration System** is the governing design document:
- §0: Purpose — single authority for configuration, eliminates HA's dual-storage split
- §1: Design principles — P1 (single canonical representation), P2 (schema is the contract), P3 (secrets never plaintext at rest), P4 (comprehensive not fatal validation), P5 (reload classification in schema not code), P6 (zero-config is valid)
- §3.1: Configuration loading pipeline — 6 stages (file read → YAML parse → tag resolve → default merge → schema validation → model construction)
- §3.2: Schema composition — core schemas (static, bundled) + integration schemas (runtime, from IntegrationDescriptor)
- §3.3: Reload mechanism — re-parse, diff, classify (HOT/INTEGRATION_RESTART/PROCESS_RESTART), atomicity rule, config_changed events
- §3.4: Secret store — AES-256-GCM encrypted, !secret and !env tag resolution, per-operation backups (AMD-16)
- §3.5: UI/API write path — optimistic concurrency via fileModifiedAt, ReentrantLock serialization, atomic flush
- §3.6: Validation error model — three-tier (FATAL/ERROR/WARNING), startup vs reload semantics
- §3.7: Configuration migration framework (AMD-13) — ConfigMigrator, MigrationResult, MigrationPreview, linear version chain
- §4: Data model — ConfigModel (§4.1), ConfigSection (§4.2), ConfigChangeSet/ConfigChange (§4.3), config_changed event (§4.4), config_error event (§4.5), ConfigIssue/Severity (§4.6), ConfigMutation (§4.7), SecretEntry (§4.8)

## JPMS Module

```
module com.homesynapse.config {
    requires transitive com.homesynapse.event;

    requires org.snakeyaml.engine.v2;
    requires com.networknt.schema;
    requires com.fasterxml.jackson.core;
    requires com.fasterxml.jackson.databind;
    requires org.slf4j;

    exports com.homesynapse.config;
}
```

The `requires transitive com.homesynapse.event` declaration is required because `HomeSynapseException` (from event-model) appears in the public API as the superclass of `ConfigurationLoadException` and `ConfigurationReloadException`, and `ConfigurationValidationException` (from event-model) appears in the throws clause of `ConfigurationService.write()`. Any downstream module that catches configuration exceptions or calls the write path needs these event-model types on its module path.

The five **third-party, non-transitive** directives were ruled in by Nick (2026-06-10, the M6.1a module-info escalation): snakeyaml-engine 2.9 and json-schema-validator 1.5.6 are explicit JPMS modules resolving on the module path, so the package-private M6.1a pipeline classes cannot compile without them; jackson-core/databind back the validator and schema composition; slf4j backs LTD-15 logging. They are consumed ONLY by package-private classes — nothing third-party leaks onto the exported API (`-Xlint:exports` silent). The **HomeSynapse-module edge set is unchanged** — the [AMD-71-A] zero-new-edge property (no `config→platform`) holds; the AMD-66/67/70/71 §7 embeds carry dated ruling-correction notes. Platform-api types (`SystemId`, `Ulid`) are read through the existing `requires transitive com.homesynapse.event → requires transitive com.homesynapse.platform` chain (implied readability), NOT a new edge.

**Note:** The original Block K handoff (Locked Decision #7) specified `requires` (non-transitive), reasoning that no event-model types appeared in public API signatures. This was incorrect — the compiler flagged it with `-Xlint:all -Werror` (`[exports]` warning). Changed to `requires transitive` to satisfy the compiler and JPMS hygiene requirements.

## Cross-Module Contracts

- **`ConfigurationService.load()` is called exactly once during startup.** It is the FIRST subsystem initialization step (Doc 12). All other subsystems receive their configuration from the loaded model. Subsequent access uses `getCurrentModel()`.
- **`ConfigurationService.getCurrentModel()` is non-blocking.** It returns the most recently loaded or reloaded model via a volatile reference. Concurrent reads from multiple subsystems are safe.
- **`ConfigurationService.write()` throws two different exception types.** `ConfigurationValidationException` (from event-model, checked) if the mutated config fails schema validation. `ConcurrentModificationException` (from java.util, runtime) if the file was externally modified since the model was loaded. Callers must handle both.
- **`ConfigModel.fileModifiedAt` is the optimistic concurrency token.** The UI/API write path checks this against the file's current mtime before writing. If they differ, an external edit occurred (text editor, scp, Git pull) and the write is rejected.
- **Reload atomicity: FATAL or ERROR in candidate → entire reload rejected.** The active ConfigModel remains unchanged. This is stricter than startup, where ERROR keys revert to defaults. The distinction exists because on startup there is no prior good state to preserve.
- **`ConfigurationAccess` is ALWAYS provided to every integration adapter.** Unlike `TelemetryWriter`, `SchedulerService`, and `ManagedHttpClient` which are optional and gated by `RequiredService` declarations, `ConfigurationAccess` is always non-null in `IntegrationContext`. Even adapters with no configuration get an empty section (INV-CE-02 — zero-config is valid).
- **`ConfigurationAccess.getConfig()` returns only the adapter's own section.** The map contains only keys under `integrations.{type}:`. The adapter cannot see global configuration or other integrations' sections. All `!secret` and `!env` values are already resolved.
- **`SchemaRegistry` parameters are JSON text strings, not library types.** This is a deliberate JPMS hygiene decision — the `networknt:json-schema-validator` library type `JsonSchema` is never exposed in the public API. Phase 3 implementation parses JSON strings internally.
- **`ConfigValidator.validate()` is a pure function with no side effects.** It validates parsed config against composed JSON Schema in allErrors mode (all issues collected in a single pass). Thread-safe and stateless.
- **`ConfigMigrator` implementations must be idempotent.** Applying the same migration twice to the same input produces the same output. The `migrate()` method does not modify the input map — it returns a new map via `MigrationResult`.
- **Reload/write publish `config.section_reloaded` ONLY (PM ruling R4, 2026-06-10 — DP-7).** One event per changed section (names + counts + classification — §12.4-safe), DIAGNOSTIC priority, `EventOrigin.SYSTEM`, null `eventTime`, system subject, via `publishRoot` (durable per INV-ES-04 when publication succeeds; publish failure never fails the reload, AMD-70-INV-01). The value-bearing `ConfigChangedEvent` remains registered in all manifests but gains **no production publish site** — Doc 06 §12.4 (Locked, security) forbids config values in event payloads and the frozen record shape is value-bearing; reconciliation is a queued FUTURE-AMD (REC-138 family).
- **`config_error` diagnostic events are produced for each ERROR-severity issue at startup (M6.4, DP-10/R1 — `load()` only, never `reload()`).** Same DIAGNOSTIC/SYSTEM/null-eventTime/system-subject metadata. The §12.4 fence: an `x-sensitive` schema path publishes `message="[REDACTED]"` and `appliedDefault="(none)"`; a null schema default publishes the literal `"(none)"`.

## Key Design Decisions

1. **ConfigModel uses `Map<String, ConfigSection>` and `Map<String, Object>` in Phase 2, not typed subsystem records.** Doc 06 §4.1 shows typed fields like `EventBusConfig`, `DeviceModelConfig`, etc. These are Phase 3 implementation details that depend on each subsystem's §9 schema content. Phase 2 carries `sections` (Map<String, ConfigSection>) for structured access and `rawMap` (Map<String, Object>) for the complete parsed-and-validated map. This gives ConfigurationAccess and ConfigurationService everything they need without depending on per-subsystem types.

2. **ConfigChange name collision resolved: reload version keeps `ConfigChange`, migration version renamed to `MigrationChange`.** Doc 06 §4.3 defines `ConfigChange(sectionPath, key, oldValue, newValue, reload)` for the reload diff. Doc 06 §3.7 defines a different `ConfigChange(type, path, oldValue, newValue, reason)` for migration. The reload version is the primary consumer-facing type (used in ConfigChangeSet, REST API, subscribers). The migration version is renamed to `MigrationChange`.

3. **SchemaRegistry uses `String` (JSON text), not `JsonSchema` library type.** Doc 06 §8.6 references `JsonSchema` in method signatures, which is a `networknt:json-schema-validator` library type. Leaking external library types in a public JPMS module API violates JPMS hygiene. Phase 2 signatures use `String` for all schema parameters. Phase 3 parses JSON strings into `JsonSchema` internally.

4. **ConfigurationAccess is REQUIRED (non-null) in IntegrationContext.** Unlike TelemetryWriter, SchedulerService, and ManagedHttpClient which are optional, ConfigurationAccess is always provided. An adapter always has configuration access for its own section — even if that section is empty (INV-CE-02).

5. **Two NEW exceptions in `com.homesynapse.config`, not in event-model.** `ConfigurationLoadException` (config.load_failed, HTTP 503) and `ConfigurationReloadException` (config.reload_failed, HTTP 422) are domain-specific to the Configuration System. They follow the exact same pattern as `ConfigurationValidationException` in event-model but live in this module's package. `ConfigurationValidationException` already exists in event-model and is NOT duplicated.

6. **`ConfigMigrator` is an interface, not an abstract class.** Doc 06 §3.7 shows it as an interface with three methods. This allows implementation flexibility in Phase 3 (lambda implementations for simple migrations, full classes for complex ones).

7. **`SecretStore.resolve()` exception type deferred to Phase 3.** The Javadoc documents `@throws IllegalArgumentException` as a placeholder. Phase 3 may introduce a `SecretNotFoundException` or reuse an existing exception type.

8. **`requires transitive com.homesynapse.event` (corrected from handoff).** The original handoff (Locked Decision #7) specified non-transitive, reasoning no event-model types appeared in public API. The compiler disagreed: `HomeSynapseException` is the superclass of both config exceptions, and `ConfigurationValidationException` is in ConfigurationService.write()'s throws clause. Changed to `requires transitive` to satisfy `-Xlint:all -Werror`.

9. **`ReloadResult` is a new record not shown in Doc 06 §4 but referenced in §8.3.** The `reload()` method needs to return the new model, the change set, and any issues. ReloadResult captures this triple.

10. **`ConfigChangeSet` convenience methods are Phase 3.** Doc 06 §4.3 shows `hot()`, `integrationRestart()`, and `processRestart()` filter methods. These are implementation logic (stream filtering), not interface specification. Phase 2 defines the record with `timestamp` and `changes` fields only.

## Gotchas

**GOTCHA: `ConfigurationValidationException` is in event-model, NOT in this module.** Do not duplicate it. `ConfigurationService.write()` references it via import from `com.homesynapse.event`. Both `ConfigurationLoadException` and `ConfigurationReloadException` are in `com.homesynapse.config`.

**GOTCHA: `ConfigChange` and `MigrationChange` are two different types.** Doc 06 uses the name `ConfigChange` for both the reload diff record (§4.3) and the migration record (§3.7). The codebase resolves this collision by renaming the migration version to `MigrationChange`. Do not confuse them — they have different fields and different purposes.

**GOTCHA: `ConfigModel` has NO typed subsystem records in Phase 2.** Doc 06 §4.1 shows `EventBusConfig`, `DeviceModelConfig`, etc. as fields. Phase 2 uses `Map<String, ConfigSection>` and `Map<String, Object>` instead. Typed records are Phase 3 additions.

**GOTCHA: `ConfigurationAccess` is non-null in IntegrationContext.** Unlike TelemetryWriter/SchedulerService/ManagedHttpClient which are nullable and gated by RequiredService, configAccess is always present. The IntegrationContext compact constructor validates it with `Objects.requireNonNull`. An adapter with no config gets an empty section.

**GOTCHA: `SchemaRegistry` parameters are JSON text strings, not file paths.** The Javadoc explicitly notes this. `registerCoreSchema("persistence", schemaJsonString)` — not `registerCoreSchema("persistence", "/path/to/schema.json")`. Phase 3 implementation parses the JSON string internally.

**GOTCHA: `json-schema-validator` IS in the version catalog and build.gradle.kts.** The `networknt:json-schema-validator` library is present as `libs.json.schema.validator` with `implementation` scope. It is available for Phase 3 implementation of `ConfigValidator` and `SchemaRegistry`.

**GOTCHA: IntegrationContext field ordering changed in Block K.** `configAccess` was inserted at position 7 (after `healthReporter`, before `schedulerService`) to group all required (non-null) fields together before optional (nullable) fields. Any code constructing IntegrationContext must include the new field.

**GOTCHA: `ConcurrentModificationException` in ConfigurationService.write() is a RuntimeException.** The Block K handoff described both exceptions as "checked" — `ConfigurationValidationException` is checked (extends HomeSynapseException extends Exception), but `ConcurrentModificationException` is unchecked (extends RuntimeException). It's declared in the throws clause for documentation purposes but does not require a catch block.

**GOTCHA: `module-info.java` uses `requires transitive`, not `requires`.** The original Locked Decision #7 was incorrect. The compiler flags it as an `[exports]` warning promoted to error by `-Werror`. Three types from event-model leak through the public API: `HomeSynapseException` (superclass ×2) and `ConfigurationValidationException` (throws clause).

**GOTCHA: `package-info.java` was repurposed, not deleted.** The handoff said to delete the scaffold. Due to VM disk space constraints preventing bash execution, it was repurposed as a proper package-level Javadoc file. This is benign and arguably better practice.

**GOTCHA (⟳ M6.1a gate-fix round 1, 2026-06-10): snakeyaml-engine's DEFAULT LoadSettings schema is the JSON schema, NOT YAML 1.2 Core — under it `~` parses as the string `"~"`, not null.** LTD-09 mandates YAML 1.2, so every `LoadSettings` the module builds MUST carry `.setSchema(new CoreSchema())` (`org.snakeyaml.engine.v2.schema.CoreSchema` — exported by the explicit 2.9 module, javap-verified). `YamlLoader` sets it on BOTH `rootSettings()` and `includedSettings(...)`; the two must stay in lockstep or the same scalar literal resolves differently depending on which file it sits in. Under the Core schema `~`/`null` (any case)/empty scalar → null = unset → normalization drops the key and the schema default applies (pinned by `YamlLoaderTest.nullValuedKeysDropped`, which FAILED on the engine default at the first M6.1a gate run). Any future LoadSettings construction site (e.g. the M6.4 reload re-parse) must carry the same schema.

**GOTCHA (RESOLVED 2026-06-10 — was the M6.1a blocker): the pipeline's third-party `requires` directives are ruled in.** snakeyaml-engine 2.9 is an explicit JPMS module (`org.snakeyaml.engine.v2`) and networknt json-schema-validator 1.5.6 is an explicit JPMS module (`com.networknt.schema`, which `requires com.fasterxml.jackson.databind` NON-transitively). Nick's 2026-06-10 ruling added exactly five non-transitive directives (snakeyaml, networknt, jackson-core, jackson-databind, slf4j) consumed only by package-private classes, plus the two Gradle lockstep lines. The "module-info unchanged" guarantee in the AMD §7 embeds is now scoped to the **HomeSynapse-module edge set** (ruling-correction notes in AMD-66/67/70/71 §7). Standing lesson: Gradle `implementation` scope does NOT exempt a named module from needing `requires` (`coder-lessons.md` 2026-06-09).

**GOTCHA: the declared `(major, minor)` pair is wired TWICE — `StandardSchemaRegistry` and `StandardConfigurationService` ctors must receive the same values.** The registry pins `schema_version.major` as a schema `const` and supplies the zero-config default pair; the service triggers migration and stamps models with its pair. The composition root owns keeping them identical; mismatched wiring makes every load fail validation (const mismatch) or stamps models with a pair the schema rejects. Both ctor Javadocs state this.

**GOTCHA (RESOLVED M6.2): `!secret` / `!env` tags now RESOLVE in the load/reload pipeline.** The M6.1 unknown-tag-FATAL staging ended with M6.2: the resolving `YamlLoader` ctor registers both constructors (root AND included documents), threaded from the service's new `secretStore`/`envLookup` ctor params. Missing key/unset variable → FATAL naming the key/var only (LTD-15), all failures collected in one pass. The WRITE-path re-parse deliberately keeps tags FATAL — see the next gotcha.

**GOTCHA (M6.2): the §3.5 write path REJECTS tag-bearing documents fail-closed.** `write()` re-parses the on-disk document with the NON-resolving one-arg `YamlLoader` and re-emits the mutated tree — if tags resolved there, the plaintext secret would be baked into the rewritten file (INV-SE-03/§12.3 violation). A document carrying `!secret`/`!env` therefore fails `write()` with `ConfigurationValidationException` ("…write path…edit homesynapse.yaml directly"), file and active model untouched. UI/API mutation of tag-bearing configs needs a tag-preserving emitter — a queued post-MVP concern, flagged `[REVIEW]` in the M6.2 completion report.

**GOTCHA (M6.2): the secret store is ONE SCOPE (`config_secrets`) in the shared key hierarchy — there is no `.secret-key` file.** Doc 15 §7.3 unified the legacy single-static-key design into the per-scope model BEFORE first release (no migration; no production secrets existed). Key files are `.root-key` (32 raw bytes, 0400 best-effort) and `scope_keys.json` ([R6]: a CONFIG-side JSON file mirroring `secrets.enc` ownership — the Doc 15 §4.1 SQLite `scope_keys` table is structurally unreachable from config under the zero-new-edge property; parked Doc-15 currency nit). `scope_keys.json` plaintext is CORRECT — every DEK in it is wrapped ciphertext.

**GOTCHA (M6.2/M6.3): two GCM nonce disciplines, one manager — keep them separate.** `ScopeKeyManager.encrypt` (the M6.2 SECRETS path) and the `secrets.enc` full-file rewrites use a fresh **random** 96-bit GCM IV per operation (occasional-write volume; collision risk negligible — DP-7). `ScopeKeyManager.encryptPayload` (the M6.3 EVENT-PAYLOAD path, now implemented) uses a per-`(scope,keyVersion)` durable **counter** nonce (Doc 15 §3.4 — random nonces hit the GCM birthday bound at event volume; OR-M6-NONCE). Do NOT cargo-cult either direction: never give secrets a counter, never give payloads a random IV. `StandardSecretStore` is untouched by `encryptPayload` (it calls `encrypt`); the only consumer of `encryptPayload` is the `com.homesynapse.app.Main` adapter (re-pointed in M6.3). `decrypt` is nonce-agnostic and serves both.

**GOTCHA (M6.2/CARRY 1): `ScopeKeyManager` does NOT implement persistence's `PayloadCipher`.** Implementing it in config would force a `config → persistence` edge. The adapter lives in `com.homesynapse.app.Main` (package-private `payloadCipher(Path, Clock)` factory), threaded through `HomeSynapseCore`'s new nullable 5-arg ctor into the lifecycle module, where it is HELD for M6.3. The Doc 15 §8.1 row saying "implement `PayloadCipher`" is the known-stale parked nit — §3.8 governs.

**GOTCHA: migration runs in memory only — the §3.7 step-7 write-back and pre-migration backup are deferred to the milestone that owns the atomic write path (M6.4).** Each load of an old-major file re-runs the chain; the `ConfigMigrator` idempotency contract makes that safe. No production migrator exists, so the gap is unreachable until the first real schema bump. Flagged `[REVIEW]` in the M6.1a completion report.

**GOTCHA: the chain selector can re-apply a same-major minor migrator below the persisted minor** (e.g. persisted 2.1 with a registered 2.0→2.1: selection is by `fromMajor ∈ [persistedMajor, declaredMajor)` only). This is the ratified reference semantics — idempotency absorbs the re-application. Do not "fix" the selector to filter by minor.

**GOTCHA: `MigrationResult` was deliberately NOT modified by AMD-67 (E67-1).** It carries no version field — only `MigrationPreview` carries the `(major, minor)` pairs. The M6.1 instruction's file table listed it MODIFY, but the ratified AMD makes the edit conditional on adding applied-version reporting, which M6.1b did not add.

**GOTCHA: `ScopedConfigurationAccess` is package-private with snapshot semantics.** It captures its section's values at construction (the `ConfigurationAccess` Javadoc promises immutability). **The M9 exposure seam LANDED in M9.1 (2026-07-02):** `ConfigurationAccess.scoped(String integrationType, ConfigModel)` — a public static interface method (the `StateQueryService.materialized(...)` gateway pattern) constructing the package-private impl intra-package; zero module-info change (the package was already exported). **GOTCHA: AMD-66 listener registration tests live with the service, not the interface.** Duplicate-section-path rejection (AMD-66 §2.4) is `StandardConfigurationService` constructor behavior (M6.1a-held). `ConfigurationChangeListenerTest` covers the interface shape + behavioral contract only. **GOTCHA (M6.4): the first-write backup fires ONCE per file lifetime, keyed on backup-file absence.** `write()` creates `homesynapse.yaml.bak.{yyyyMMdd'T'HHmmss'Z'}` (ISO-8601 BASIC format — the extended form's colons are illegal on Windows; stamp from the injected Clock) only when NO `homesynapse.yaml.bak.*` exists in the config dir. The Doc-06-era spec text says `config.yaml.bak.*` — the implementation uses the AMD-71 root-document name; flagged `[REVIEW]` at M6.4.

**GOTCHA (M6.4, DP-7 ruling R4): `ConfigChangedEvent` is registered everywhere but published NOWHERE.** Doc 06 §12.4 forbids config values in event payloads; the frozen `(configPath, previousValue, newValue)` shape is value-bearing. The §3.3 step-6 notify obligation is discharged by `config.section_reloaded` instead. Do NOT add a `ConfigChangedEvent` publish site — that requires a FUTURE-AMD (REC-138 family). If an implementation need arises, STOP and escalate.

**GOTCHA (M6.4): the reload diff attributes each leaf change to its IMMEDIATE containing section only.** `ConfigModelDiff` skips keys whose values are maps on both sides — `persistence.retention.max_days` changing produces a change (and an event) for `persistence.retention`, while `persistence` stays silent. Consequence: an AMD-66 listener registered at an ANCESTOR path (e.g. `persistence`) is NOT consulted for nested-leaf-only changes — register listeners at the section that directly holds the keys. Flagged to the PM at M6.4 for the M9 supervisor wiring decision.

**GOTCHA (M6.4): reload rejection precedes listener invocation.** On a FATAL/ERROR candidate the listeners are never called (C5's "no listener side effects applied" implemented as not-invoked, which also gives validation rejection deterministic precedence over listener rejection). A listener therefore only ever observes candidates that passed validation.

### Consumption by Downstream Modules

Downstream modules that depend on these fixtures must declare **both** of the following in their `build.gradle.kts`:

testFixturesImplementation(testFixtures(project(":config:configuration")))
